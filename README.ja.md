# Branchdesk

[English](README.md) · [한국어](README.ko.md) · **日本語**

Windows と WSL の Git リポジトリを、1 つのアプリで管理するローカル Git GUI です。Windows のリポジトリは Windows の Git、WSL のリポジトリは選択したディストリビューションの Git と Python で処理します。現在のアプリ画面は韓国語です。この文書には画面上のボタン名も記載しています。

## Windows で起動する

Windows 11 x64 で `Branchdesk.exe` をダブルクリックします。EXE にはアプリ、画面、アイコン、セットアップ用スクリプトが含まれます。Microsoft Edge と、Git を実行する環境の Python 3.9 以上・Git 2.28 以上が必要です。アプリの実行にフロントエンドのビルドや外部 Python パッケージは不要です。

| PC の状態 | 起動方法 |
| --- | --- |
| 既存の WSL が利用可能 | 従来どおり既定の WSL 環境で起動 |
| WSL を使わない Windows | 起動時の画面で Windows の Python・Git 実行ファイルを選択 |
| Windows に Python・Git がない | **앱 전용 폴더에 설치**（アプリ専用フォルダーにインストール）を使用 |
| WSL を使いたい | **WSL 방식 사용** を選び、Ubuntu/Debian 用の案内に従う |

Windows の既定のツール保存先は `%LOCALAPPDATA%\Branchdesk\tools` です。Python は `python\python.exe`、Git は `git\cmd\git.exe` を接続します。インストールには WinGet を使用し、パッケージマニフェストのハッシュを検証します。WinGet は Microsoft の「アプリ インストーラー」に含まれます。既存のインストールが見つかった場合は、新しい場所への複製を期待せず、その実行ファイルを接続してください。

WSL の自動パッケージインストールは Ubuntu/Debian 系に対応します。WSL の初回導入には管理者の承認、再起動、Linux アカウントの作成が必要な場合があります。既存のディストリビューションを置き換えたり、既定のディストリビューションを変更したりはしません。Windows に Edge が必要です。

### Windows・WSL2 環境を追加する

1. 上部の **실행 환경**（実行環境）を開きます。
2. **＋ 실행 환경 추가**（実行環境の追加）を押します。
3. **Windows** または **WSL2** を選び、名前を確認します。WSL のディストリビューション名は省略できます。
4. **이 환경 연결하기**（この環境に接続）を押すと、Python・Git の場所とバージョンを確認します。
5. 自動検索できない場合や特定のバージョンを使う場合は、**프로그램 경로 직접 지정**（実行ファイルのパスを指定）を開きます。

一覧には「現在の OS」という曖昧な表記ではなく、実際の種類とディストリビューションを表示します。Linux 上でソースから起動した場合は Linux 環境も選択できます。既存の環境 ID とリポジトリの接続は維持します。

**저장소 열기**（リポジトリを開く）で環境と、その環境から見たパスを選択します。

| 環境 | パスの例 |
| --- | --- |
| Windows | `C:\projects\my-app` または `C:/projects/my-app` |
| WSL2 | `~/projects/my-app` または `/home/user/projects/my-app` |

リポジトリを開く画面にも環境追加ボタンがあります。追加後に戻っても、入力途中のクローン URL やフォルダーは保持されます。各タブは環境とパスを記憶します。Git・Python のパス選択はアプリの設定であり、システムの PATH や Git のグローバル設定を変更しません。明示的にツールをインストールした場合、インストーラー自身が PATH を登録することはあります。

**Git·Python이 없나요? 프로그램 설치** を開くと、不足するツールを導入できます。Windows はユーザーの指定フォルダー、WSL はディストリビューションのパッケージ管理機能を使用します。完了後に接続、または設定を保存してください。

**앱 시작 설정 (고급)** は、次回 EXE を起動する Python 環境の設定です。各リポジトリの Git 環境とは別で、通常は変更不要です。Windows と WSL のホストを切り替える場合は、環境設定とタブの参照を移行先の状態フォルダーに統合します。リポジトリや秘密鍵の実体はコピーしません。アプリ起動には Windows または既定の WSL を使用し、それ以外の WSL もリポジトリ用には接続できます。

Windows と WSL の Git ユーザー情報、認証、改行設定、SSH エージェントは独立しています。同じ作業ツリーを複数の Git 環境で同時に操作せず、改行の共通ルールは `.gitattributes` で定義してください。

### SSH 鍵を接続・生成する

保存した環境の **SSH 키 연결 · 관리** を開きます。秘密鍵のパスを入力するか、**기존 키 찾기** でその環境の `.ssh` フォルダーから選びます。**공개키 보기/복사** は Git サービスに登録する公開鍵だけを表示・コピーします。**SSH 설정 저장** で保存してください。秘密鍵の内容を画面や API 応答に返したり、`~/.ssh/config` や Git のグローバル設定を書き換えたりはしません。鍵の指定を空にすると既存の Git/SSH 認証を使用します。

新しい Ed25519 鍵は `~/.ssh/branchdesk-NAME/id_ed25519` に作成します。同じ名前のフォルダーがあれば上書きせず中止します。アプリから生成する場合は、パスフレーズなしの鍵を作るチェックボックスを明示的に選択する必要があります。パスフレーズ付きの鍵は、その環境のターミナルで `ssh-keygen -t ed25519` を実行して作成し、接続後に `ssh-add` でエージェントに登録してください。WSL/Linux の `SSH_AUTH_SOCK` が継承されない場合は、設定でエージェントのソケットを指定できます。Windows OpenSSH は Windows のエージェントサービスを使います。

認証確認は GitHub、GitLab.com、Bitbucket に対応します。未知のホスト鍵を自動承認しません。対象環境で `ssh -T git@HOST` を実行し、サービスが公開している指紋を確認してください。公開鍵のサービスへの登録は利用者が行います。社内サーバーや独自の接続条件はターミナルで確認してください。

## 主な操作

| 操作 | 動作 |
| --- | --- |
| リポジトリのタブ | 既存フォルダー、クローン、新規作成に対応。再起動時にタブの順序と選択を復元し、最近使ったリポジトリも再表示 |
| ブランチをシングルクリック | チェックアウトせずコミットを選択し、グラフをその位置へスクロール。必要に応じて最近 5,000 件まで追加検索 |
| ローカルブランチをダブルクリック | **브랜치 변경 확인**（ブランチ変更の確認）を表示してから切り替え |
| クリーンな切り替え | **청소** は既定でオフ。明示的に選ぶと、一覧に表示した変更、ステージ済み変更、新規ファイルを破棄。無視対象と入れ子の Git リポジトリは保持。確認後に状態が変わると拒否 |
| ファイル状態・コミット | ファイル全体や選択した変更行をステージ／解除。コミット、直前のコミットの修正 |
| 新規ファイル | 比較する旧ファイルがなくても、選択した版の全文を行番号付きで表示。ステージはインデックス、コミットはそのコミットの内容を読む。空・バイナリ・制限到達は理由を表示 |
| 履歴・比較 | コミットの詳細、2 コミットの比較、一覧／フォルダーツリー表示。ファイルのダブルクリックでプレビューを拡大 |
| リモートの Web ページ | **원격** は既定のブラウザーで GitHub・GitLab・Bitbucket などのリポジトリを開く。SSH/HTTPS を認証情報を除いた Web URL に変換。複数ある場合は選択。ローカルパスには Web ページなし |
| リモート設定 | **원격 설정** で fetch/push URL の確認・コピー、追加、変更、接続削除 |
| fetch・pull・push | リモートとブランチを選択。fetch の prune/tags、既定の fast-forward-only pull と merge/rebase、upstream を設定する push |
| ブランチ・タグ | 作成・名前変更・マージ済みローカルブランチ削除、リモート追跡、rebase、タグ作成・削除・push |
| stash・競合 | 保存、apply/pop/drop、直接編集または片側の採用による解決、処理の続行・中止 |
| ターミナル・エクスプローラー | 対象の Windows/WSL 作業フォルダーで開く。Windows Terminal があれば新しいウィンドウ、なければ PowerShell。同じフォルダーのエクスプローラーは再利用 |
| ウィンドウ表示の案内 | 対象ウィンドウを復元して前面化。Windows に拒否された場合は見つかったウィンドウのタスクバーボタンを点滅させ、アプリにも案内 |
| 外部の編集を反映 | **새로고침**（更新）を押す |

通常のブランチ切り替えは、Git が維持できるローカル変更を引き継ぎ、競合する場合は中止します。**청소** は破棄操作です。対象の一覧を確認してから確定してください。

全文プレビューは UTF-8 と BOM 付き UTF-16 に対応し、最大 192 KiB・3,000 行まで表示します。超過時は省略を明示します。行単位ステージは、各版 256 KiB・5,000 行以下の UTF-8 通常テキストが対象です。履歴は最初に 150 件、最大 5,000 件を読み込み、検索は読み込み済みの範囲が対象です。名前変更は削除と追加で表示します。

### メニュー・レイアウト・Git Flow

ブラウザー標準の右クリックではなく、コミット、ブランチ、タグ、ファイル、タブ、テキスト入力用のメニューを表示します。サブメニューはマウスと矢印キーで操作でき、Shift+F10 でメニュー、Enter で実行、Esc で閉じます。入力欄はコピー・切り取り・貼り付け・全選択・元に戻すに対応し、クリップボード権限がない場合は Ctrl+V を使用できます。F5 はページ再読み込みではなくリポジトリ更新です。

ペインの境界をドラッグするか、境界にフォーカスして矢印キーで幅を調整します。ウィンドウの位置・サイズ・最大化状態は一時的な Edge プロファイルとは別に保存し、再起動やアプリ更新後に復元します。最小化したまま終了しても、次回は通常状態または元の最大化状態で開きます。モニター構成が変わると Windows が画面外の配置を調整します。

コミットメニューは detached HEAD でのチェックアウト、選択コミットへの merge/rebase、ブランチ・タグ作成、親を指定する revert/cherry-pick、reset、アーカイブ／パッチの出力、SHA コピー、外部 diff を提供します。hard reset は `HARD` の入力が必要です。コミット順序の整理は、クリーンなローカルブランチの線形履歴で、基準以降 100 コミットまでの pick/squash/fixup/drop に対応します。アーカイブ／パッチは原本 12 MiB までで、マージコミットの単一 format-patch 出力は非対応です。外部比較はその環境の `diff.tool` を使用します（Ctrl+D）。

**Git Flow** では本番／開発ブランチを設定し、`feature`、`release`、`hotfix` を開始します。feature は開発から分岐して開発へ完了し、release/hotfix は両方へ完了してバージョンタグを作成します。完了処理は一時的な worktree でマージを準備し、1 つの Git トランザクションで参照を更新します。競合時は更新前に停止します。ブランチとタグの push は別操作です。

## アプリの更新

**앱 업데이트 → 새 버전 받기 → 적용 후 재시작** を使用します。更新機能がない古い EXE を使っている場合だけ、終了して一度 `git pull` し、新しい EXE を起動してください。

このリポジトリの `main` にある `Branchdesk.exe` と実行中のファイルを比較し、コミットに固定した blob をバックグラウンドで取得します。Git blob ハッシュと Windows 実行ファイル形式を検査し、Windows 側の保存時に SHA-256 も確認します。適用時はタブと作成途中のコミットメッセージを保存して終了し、新しい EXE を起動します。復元情報は Windows/WSL のホスト変更でも共有します。

保存先は `%LOCALAPPDATA%\Branchdesk\versions\<hash>\Branchdesk.exe` です。以後、認識済みの旧 EXE から起動しても保存済みの新しい版に接続します。`git pull` で取得した未知の新しい EXE はそちらを優先します。ダウンロードやヘルパーの検証に失敗した場合、現在のアプリを維持します。

**アプリ更新は `git pull` を実行しません。** 実行するアプリを更新する方式なので、ソース、README、ローカルの編集、元の EXE はそのままです。ソースの更新には別途 `git pull` を実行してください。Git・Python 自体のインストール管理も別です。自動適用は Windows EXE での起動が対象で、ソース起動には適用しません。

## ソースからの起動・ビルド

```bash
python3 branchdesk.py
python3 branchdesk.py ~/projects/project-a ~/projects/project-b
python3 branchdesk.py --no-browser
```

Windows では環境に応じて `python` を使用します。ブラウザーが開かない場合は、ターミナルに表示されたローカル URL 全体を開きます。Ctrl+C でソースのサーバーを終了します。Python 標準ライブラリーと Git 以外の実行依存はありません。

WSL/Linux で他のフォルダーから呼ぶ場合は、パスを調整して `~/.bashrc` に追加します。

```bash
alias branchdesk='python3 "$HOME/tools/branchdesk/branchdesk.py"'
```

Windows の C++ デスクトップ開発ツールと Python を導入した上で、Visual Studio の **x64 Native Tools Command Prompt** で実行します。

```bat
py -3 windows/build.py
```

出力は `dist/Branchdesk.exe` です。Linux では MinGW-w64 の GCC と windres がある環境で `python3 windows/build.py` を使います。アプリ更新で配布する変更には、ルートの `Branchdesk.exe` の再ビルド版もコミットしてください。

## ローカル状態と通信

| データ | 保存先 |
| --- | --- |
| Windows の環境設定・タブ | `%LOCALAPPDATA%\Branchdesk\state` |
| WSL/Linux の環境設定・タブ | `~/.local/state/branchdesk`、または `XDG_STATE_HOME` に対応する場所 |
| ウィンドウの位置・サイズ・最大化 | `%LOCALAPPDATA%\Branchdesk\window.bin` |
| EXE の版と更新先 | `%LOCALAPPDATA%\Branchdesk\versions` と `current.json` |
| デスクトップ更新の復元情報 | `%LOCALAPPDATA%\Branchdesk\resume-ui.json` |

EXE は Windows のループバックでのみ接続を受け付けます。認証付き HTTP 要求は専用のバイナリパイプを通って Python 環境へ渡されるため、WSL の localhost 転送は不要です。各アプリウィンドウは独立した一時 Edge プロファイルを使います。終了時は受け付け済みの Git 処理が完了してからバックエンドを終了します。

## 検証

```bash
python3 -m unittest discover -s tests -v
# 任意: テスト時だけ Playwright Python と Chromium が必要
python3 tests/browser_smoke.py
BRANCHDESK_EXE=./Branchdesk.exe python3 tests/browser_smoke.py
```

一時リポジトリとローカル bare リモートを使用し、Git 操作、環境・ワーカー通信、SSH 鍵の保護、版を区別したファイルプレビュー、クリーン切り替えの保護、履歴内の位置検索、リモート URL と認証情報除去、更新の失敗処理を検証します。ブラウザーテストはメニュー、プレビュー、ブランチのクリック／ダブルクリック、リモート選択、外部ウィンドウの案内、更新を確認します。Linux 上では Windows プロセスの実起動をモックに置き換えます。

準備済みの Windows 11 デスクトップでは次を実行できます。

```powershell
.\windows\test-launch.ps1
.\windows\test-window-state.ps1
```

配置テストの前に他の Branchdesk を閉じてください。通常の位置・サイズ、最大化後の再起動、最小化したままの終了を検証し、元の配置ファイルを復元します。Windows の実際のインストール、前面化、複数モニター、更新後の再起動は Windows 上で別途検証する必要があり、Linux のテストでは実行しません。
